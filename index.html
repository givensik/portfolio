프로젝트 01 — CLEAR (1/2)

CLEAR

Contextual Leak Evaluation And Redaction — MCP 기반 LLM 에이전트 DLP 게이트웨이

기간 2026.03 – 2026.06 소속 세종대 캡스톤디자인 (팀 세이레네스 4인) 역할 MCP Gateway 전담 + 전체 모듈 통합 및 성능 평가 담당 저장소 github.com/sejong-capstone-seirenes/clear

CLEAR는 LLM 에이전트가 MCP로 기업 내부 도구(파일·Notion·DB 등)를 자율 호출하는 환경에서, 정규식/키워드 기반 기존 DLP가 막지 못하는 맥락적 데이터 유출 — 특히 여러 도구의 반환값이 만드는 결합정보 기반 재식별 위협 — 을 차단하는 동적·계층형 방어 게이트웨이다. 에이전트와 하위 MCP 서버 사이에 프록시를 두고, 사용자 프롬프트(I)·툴 콜(T)·반환값(R)을 맥락으로 LLM Judge가 과다 노출을 평가, Filtering 계층이 민감 정보만 선별 마스킹(R')한다. 본인은 통신 레이어인 MCP Gateway(stdio·HTTP 2종)를 전담하고, 팀원이 만든 Judge·Filter 모듈을 하나의 end-to-end 파이프라인으로 통합했다.

① 하위 MCP 서버 동적 툴 프록시

How어떻게 구현했는가

참조 아키텍처인 Lasso Security 오픈소스 MCP Gateway의 프록시 기능을 일부 수정하여 사용하였다 (플러그인 방식이 LangGraph 기반 DLP 워크플로우와 맞지 않아 MCP SDK 위에 자체 구현). 게이트웨이는 기동 시 하위 서버의 tools/list JSON Schema를 inspect.Parameter로 시그니처 조립해 프록시 툴로 동적 등록하는데, 이 'JSON Schema → 파이썬 시그니처' 변환에서 두 결함을 발견했다.

  • 버그 ①  하이픈 든 비식별자 파라미터(Notion-Version)가 isidentifier()에서 ValueError → 툴 등록 누락
  • 버그 ②  required 무시로 전부 필수 등록 → optional 파라미터(start_cursor)를 생략 못 해 호출 교착

해결  "내부에선 안전한 이름으로 변형 → 하위 서버 위임 경계에서 원본 복원" 원칙 + required 우선 정렬.

Why왜 그렇게 설계했는가

게이트웨이는 어떤 MCP 서버가 붙어도 동작해야 하므로, 특정 스키마에 하드코딩하지 않고 변환 규칙 자체를 일반화해야 한다. 변형은 내부 구현으로 감추고 경계에서 원본을 복원하면, 상위 에이전트와 하위 서버 양쪽 모두 원래 스키마를 그대로 본다.

Result어떤 효과가 있었는가

Notion·filesystem 등 하이픈·optional 파라미터가 섞인 실제 MCP 서버를 스키마 손실 없이 프록시할 수 있게 됐다. 나아가 이 두 결함이 원본 lasso-security mcp-gateway에도 그대로 존재함을 확인해 GitHub Issue #19·#20으로 제보(2026.06)했다.

mcp-gateway/mcp_gateway/gateway.py — 스키마 → 시그니처 변환 핵심

# 하이픈 파라미터(Notion-Version)는 isidentifier 실패 → 내부에선 안전한 이름으로 변형

② OARM Matrix 분류 + DLP workflow 라우팅

How어떻게 구현했는가

가로챈 모든 tools/call을 OARM Matrix로 Broad Read / Atomic Read / Other로 분류한다. Read 계열(과다 반환 위험)은 LangGraph workflow(Judge→Filter)로 라우팅해 DLP 검증을 거치게 하고, 그 외(쓰기·기타)는 하위 서버로 직접 위임한다. Matrix는 별도 HTTP API로 분리해 분류표를 런타임에 조회·수정할 수 있게 했다.

Why왜 그렇게 설계했는가

모든 호출을 LLM Judge로 보내면 지연·비용이 과도하다. 유출 위험이 실재하는 Read 계열만 선별해 검증 파이프라인으로 보내고 나머지는 우회시켜, 가용성을 해치지 않으면서 검증 대상을 좁혔다.

Result어떤 효과가 있었는가

분류 기준이 코드가 아닌 데이터(분류표)로 분리되어, 새 도구가 추가돼도 Gateway 재배포 없이 분류 정책을 갱신할 수 있다.

프로젝트 01 — CLEAR (2/2)

③ 분산 감사 로그 파이프라인 (turn_id / request_id) + OpenSearch

How어떻게 구현했는가

MCP에는 "턴(turn)" 개념이 없어, 같은 사용자 프롬프트에서 파생된 연속 툴 콜을 묶을 식별자가 없다. 시간 윈도우 기반으로 turn_id를 생성하고 개별 호출에 request_id를 부여해, Gateway→Judge→Filter 전 모듈의 로그를 하나의 요청 단위로 연결했다. 로그는 백그라운드 큐로 OpenSearch에 비동기 적재하며, graceful shutdown과 인덱스 템플릿 자동 등록을 포함한다.

Why왜 그렇게 설계했는가

결합정보 기반 유출은 단일 호출이 아니라 "같은 턴 안에서 누적된 여러 호출"에서 발생하므로, 호출들을 턴 단위로 묶어야 누적 노출 범위를 평가할 수 있다. 적재를 비동기로 분리한 이유는 로그 I/O가 도구 호출 응답 지연으로 이어지지 않게 하기 위함이다.

Result어떤 효과가 있었는가

대시보드에서 하나의 턴이 일으킨 전체 파이프라인 흐름을 추적할 수 있고, 동일 턴 내 이전 호출이 가져간 데이터까지 포함해 over-fetching을 판단할 수 있게 됐다.

④ DLP Dashboard — Trace 시각화 + Matrix 편집

How어떻게 구현했는가

모듈별 로그 조회와 함께, 턴 단위 파이프라인 흐름(Input → Agent → Gateway → Matrix → Judge → DLP → R')을 SVG 그래프로 시각화하는 Trace 탭을 개발했다(반응형). Matrix HTTP API와 연동해 도구 분류표를 화면에서 실시간 편집할 수 있게 했다.

Result어떤 효과가 있었는가

로그 텍스트를 일일이 읽지 않아도 어느 단계에서 무엇이 마스킹·차단됐는지 한눈에 파악되어, 데모와 디버깅 모두에서 검증 효율이 높아졌다.

⑤ 트러블슈팅 — LLM 검증 지연으로 인한 MCP 클라이언트 타임아웃

Problem무엇이 문제였는가

Read 계열 호출은 Judge(LLM)·Filter 검증을 거치기 때문에 응답이 길어졌고, 그 사이 MCP 클라이언트가 응답이 없다고 판단해 타임아웃으로 호출을 끊었다.

How어떻게 해결했는가

검증 단계를 줄이거나 설계를 바꾸는 대신 MCP 프로토콜 공식 문서를 직접 분석해, 처리 중임을 클라이언트에 알리는 progress notification을 검증 동안 전송하도록 구현했다.

Result어떤 효과가 있었는가

DLP 검증 파이프라인을 그대로 유지하면서 타임아웃 없이 도구 호출이 완료되도록 했다.

핵심 성과 — k-익명성 벤치마크

결합정보 기반 재식별에 대한 방어력을 검증하기 위해, 100만 건 합성 페르소나 데이터셋(nvidia/Nemotron-Personas-Korea)으로 No Filter / Presidio DLP / CLEAR 3개 비교군의 k-익명성을 측정하는 벤치마크를 설계·실행했다 (n=500, 총 1,589회 실행).

  • 3단계 누적 수집 시 No Filter는 median k=284까지 급감 (k≤10 극단 재식별 4.7%, 사실상 개인 특정 가능)
  • 단순 PII 마스킹(Presidio)은 k≤10 비율 3.8%로 No Filter(4.7%)와 통계적으로 동일 — 명시적 PII 차단만으로는 서사 기반 재식별을 못 막음을 실증
  • CLEAR는 median k=2,108 유지 (No Filter 대비 7.4배), k≤10 비율 0.9%로 극단 재식별을 5.2배 감소

프로젝트 03 — V2X CAM 변조 탐지

V2X CAM 변조 공격 탐지

Prediction-AutoEncoder 기반 cross-domain 비지도 이상탐지 — 정보보호학회논문지 2026.2 게재

기간 2025 (학부연구생) 게재 정보보호학회논문지(JKIISC) 2026년 2월호 저자 김준식, 서예린, 김민규, 김종현

C-ITS에서 차량은 위치·속도·방향을 담은 CAM(Cooperative Awareness Message)을 주기적으로 방송한다. 합법 인증키로 허위 CAM을 보내는 변조 공격은 암호학적 무결성만으론 막기 어려워 데이터 기반 이상탐지가 필요하다. 문제는 5G 환경엔 CAM 변조 공격 데이터셋이 없고, 공개된 공격 데이터셋은 DSRC(802.11p) 기반(VeReMi)뿐이라는 점이다. 다만 ETSI CAM 메시지 형식은 DSRC와 5G C-V2X에서 동일하므로, DSRC 공격 데이터셋을 5G 환경의 탐지 검증에 대체 활용할 수 있다 — 5G 실측 정상 데이터(V2AIX)로 학습한 비지도 모델(Prediction-AE)을 DSRC 공격 데이터(VeReMi)로 평가하는 cross-domain 설정의 타당성을 실험으로 보였다.

① cross-domain을 가능케 한 데이터 통합·정규화 (핵심 기여)

How어떻게 구현했는가

학습은 실제 5G 기반 실측 데이터(V2AIX, 정상만), 평가는 IEEE 802.11p(DSRC) 시뮬레이션 공격 데이터(VeReMi Extension)를 사용했다. 두 데이터셋을 ETSI CAM 스펙 단위로 정규화하고 위/경도를 로컬 미터 좌표로 변환했다. CAM 물리·동역학 정보 중 13개 피처를 선정(인접 프레임 위치 변화량 dpos 포함)하고, V2AIX 기준 StandardScaler를 VeReMi에 동일 적용해 도메인 분포 이동을 최소화했다.

Why왜 그렇게 설계했는가

두 데이터셋은 무선 기술·수집 환경이 달라 분포가 어긋나므로, 학습 도메인(V2AIX) 기준 표준화 파라미터를 평가 도메인에 고정 적용해야 평가 시 성능 차이가 도메인 불일치가 아닌 실제 이상 신호에서 비롯됐다고 말할 수 있다. CAM 형식이 동일하다는 표준적 사실을 정규화로 '실측 가능한 cross-domain 전제'로 바꾼 것이 이 단계의 핵심이다. (평가셋은 라벨이 정교한 VeReMi Extension을 써, 공격 전 정상 구간까지 공격으로 표시되는 함정을 피했다.)

② Prediction-AutoEncoder 모델 (예측 기반 비지도)

How어떻게 구현했는가

재구성이 아니라 다음 시점을 예측하도록 학습하는 Prediction-AE를 적용했다 — 시퀀스 L=5, CAM 13개 피처를 2-layer LSTM(hidden=128, dropout=0.3)으로 인코딩 후 MLP로 다음 1시점을 예측하고, 예측 오차(MSE)를 이상 점수로 쓴다. 정상(V2AIX)만으로 학습(Adam, lr=1e-3, batch=128, epoch=50, early stopping)하되, station 단위 80/20 분할로 동일 차량의 학습–검증 누수를 차단했다. (재구성보다 예측 오차가 시간적 일관성을 직접 모델링해 궤적 변조에 민감)

핵심 결과

  • cross-domain 유효성 실증 — 5G(V2AIX) 정상으로 학습한 모델이 DSRC(VeReMi) 공격 평가에서 위치·궤적이 비현실적으로 깨지는 공격(Random Position·Data Replay·Traffic Congestion)을 F1 0.98+로 탐지 → 무선 기술이 달라도 ETSI CAM 표준을 공유하면 탐지 모델이 그대로 이전됨
  • DSRC → 5G → 6G 전환에도 탐지 모델의 연속성 확보 가능성 제시 (CAM 표준 유지 시 재학습 없이 확장)
  • (보조) 메시지 단위로 약한 공격(DoS·Random Speed)은 차량 단위 집계로 보완 — 예: DoS_random F1 0.010 → 0.843
